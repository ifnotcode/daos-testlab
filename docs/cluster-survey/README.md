# Обследование чужого кластера, где не работает патч

Комплект для ИИ-агента (например, на DeepSeek V4) с доступом к тестовому кластеру. Агент собирает
сведения о кластере, чтобы его конфигурацию можно было повторить в этой лаборатории и
воспроизвести сбой.

| Файл | Что это |
|---|---|
| `AGENT.md` | Инструкция агенту (на английском, она точнее для модели) |
| `survey.sh` | Сборщик, который только читает. Режимы: `node` (узел), `k8s` (кластер через kubectl), `pod <ns> <pod>` (сбойный под) |
| `probe.sh` | Проверки изнутри пода через `kubectl exec`, когда нет доступа к узлам. В поде приложения: ядро узла, что смонтировано в томе и есть ли idmap. В привилегированном поде с `hostPID` (агент DAOS): все dfuse узла, их аргументы и метка сборки |
| `ROUND2-ml_test.md` | Задание на второй проход по стенду ml_test |
| `reports/` | Полученные отчёты |

Что делает агент по инструкции:
- узнаёт у оператора точный симптом;
- запускает `survey.sh`;
- проходит по цепочке условий, нужных для работы `--allow-idmap`;
- пишет `REPORT.md` по шаблону. В нём есть YAML-блок, который переносится в профиль
  лаборатории.

## Как использовать

1. Отдайте агенту `AGENT.md` как задание и положите рядом `survey.sh`. Первым сообщением можно
   написать: «Follow AGENT.md. Ask me before anything that is not read-only».
2. Отвечайте на его вопросы:
   - что именно не работает и что было развёрнуто;
   - можно ли оставлять в отчёте внутренние имена и IP;
   - разрешения на любые действия, которые не только читают.
3. Получите `REPORT.md` и архивы `survey-*.tar.gz`. Перед передачей сюда просмотрите их сами:
   сборщик маскирует значения, похожие на пароли, токены и ключи, но имена и адреса не трогает.
4. Отдайте отчёт и архивы в сессию с лабораторией. По YAML-блоку отчёта собирается профиль
   `profiles/<кластер>.conf`, затем сбой воспроизводится.

## Что проверено

`survey.sh` проверен 10.10.2026 на k8s-1 этой лаборатории. Работали csi-daos, mount-поды с dfuse
и под `hostUsers: false` без `--allow-idmap`. Сборщик нашёл всё нужное:
- процессы dfuse внутри контейнеров, их аргументы, метку сборки и версию fuse;
- опции FUSE-монтирования;
- `client_user_map` агента;
- конфигурацию kubelet;
- событие пода с `MOUNT_ATTR_IDMAP`.

Маскирование проверено на образцах: ключи, сертификаты, токены и пароли, значения env с такими
именами, длинные base64. Хеши и пути при этом остаются.

## Метка сборки dfuse

Самая быстрая проверка, тот ли dfuse запущен. Она видна по сообщениям внутри бинарника
(`survey.sh` показывает их и для процесса в контейнере):

| В бинарнике | Значит |
|---|---|
| `Idmapped mounts allowed` и `Kernel does not support idmapped mounts` | PR 1 и PR 2: опция работает (на ядре ≥ 6.12) |
| только `Fuse library does not support idmapped mounts` | только PR 1, fused старый: опция ничего не делает |
| ничего | патча нет, или другой патч idmap: вариант коллег `idmap-v2` включает idmap всегда, без опции и без этих сообщений |
