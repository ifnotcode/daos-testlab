## Результат

| Проверка | Исходный драйвер | Исправленный драйвер |
|---|---|---|
| Под с `hostUsers: false` запускается, `/mnt/daos` — `fuse.daos` с `idmapped` | да | да |
| uid 1234 пишет и читает, владелец в поде 1234:1234 | да | да |
| dfuse работает и запущен с `--allow-idmap` | да | да |
| Драйвер не перезапускается сам | да | да |
| **После перезапуска пода драйвера dfuse ещё работает** | **нет** | да |
| **После перезапуска драйвера под читает том** | **нет: `Transport endpoint is not connected`** | да |
| Пересозданный под запускается и читает | да | да |

С исходным драйвером в лаборатории получилось ровно то, что `probe.sh` показал на их стенде:
- том есть, он idmapped, но не подключён;
- dfuse на узле нет.

Причина в устройстве драйвера: dfuse живёт в контейнере драйвера. Любой перезапуск этого
контейнера (обновление, OOM при лимите 512Mi на драйвер вместе со всеми dfuse, liveness, удаление
пода) убивает все dfuse узла. Тома работающих подов при этом обрываются. **Патч `--allow-idmap`
здесь ни при чём:** до перезапуска idmap работает полностью.

Исправленный драйвер (исправление 4, mount-поды, `dfuse.mountMode: pod`) это переживает.

## Что сказать коллегам

1. Сам патч на их стенде работает. Это доказывает флаг `idmapped` у тома пода с
   `hostUsers: false`, а такое монтирование возможно только с dfuse, разрешившим idmap.
2. `Transport endpoint is not connected` — это перезапуск или падение контейнера, в котором жил
   dfuse. Проверить по рестартам и возрасту подов в `daos-csi-driver` и `daos-mount-supervisor` на
   этом узле и по событиям (OOMKilled, liveness). Если `daos-mount-supervisor` — их способ вынести
   dfuse, стоит проверить, переживает ли dfuse перезапуск супервизора.
3. Временное лечение — пересоздать под. Постоянное — dfuse вне контейнера драйвера (наше
   исправление 4 или csi-daos).
4. Попутно:
   - агент сопоставляет неизвестные uid с `nobody:nobody`, поэтому собственные подключения к
     DAOS из подов с `hostUsers: false` получат `DER_NO_PERM` без `nobody@` в ACL;
   - перехвата для uid 1234 через handles dfuse не будет: так задумано;
   - на InfiniBand перехвату в поде нужен доступ к RDMA-устройствам.

## Оговорки

- **Образ `colleagues-csi:repro` для этого сценария не годится.** В нём собран `main.go`-заглушка
  без health-сервера, поэтому liveness из chart перезапускает драйвер каждые ~40 с. Первый прогон
  с ним дал ложную картину, и в сценарий добавлена проверка рестартов драйвера.
- **Эффект `nobody:nobody` в лаборатории не выделен.** `daos pool query` из пода падает с
  `DER_TIMEDOUT`, потому что из сети подов в лаборатории нет пути к серверу. Сопоставление с nobody
  проверено только по конфигурации.
- **`daos-mount-supervisor` не воспроизведён:** его содержимое неизвестно.
